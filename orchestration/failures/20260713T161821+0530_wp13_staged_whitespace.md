# Failure report

## Task

Final staged-content whitespace audit for the WP13 root-cause-attribution closure.

## Failed command

```bash
git diff --cached --check
```

## Error

Git reported trailing-whitespace errors in two forms:

- Four metadata lines in `orchestration/reports/wp13_attribution_validation.md` end with two spaces used as Markdown hard breaks.
- Every record in `reports/attribution/wp13_predictions.csv` ends with CRLF, so the carriage-return byte was reported as trailing whitespace.

The command exited with status 2. No commit was made.

## Files changed before failure

The staged WP13 closure contains documentation, governance records, manuscript sources and PDF output, validation JSON/CSV artifacts, and figures. `git status --short` at diagnosis showed 25 staged paths and no unstaged changes. This failure report is the only file added after the failed audit and is intentionally unstaged pending recovery approval.

## Read-only diagnosis

`sed -n '1,6l' reports/attribution/wp13_predictions.csv` shows `\r$` at each record boundary. The scientific artifact is therefore CSV text with RFC-style CRLF records, not rows containing meaningful trailing spaces. Its exact bytes are already bound to the recorded SHA-256 checksum `8108f514930f6f2bfaf77bab5597e35432d6dded3c7290bfa34a294820f494eb`.

The repository already handles the same condition for the frozen WP12 CSV artifact with this scoped rule:

```gitattributes
reports/early_warning/*.csv whitespace=cr-at-eol
```

No matching attribute currently applies to `reports/attribution/wp13_predictions.csv`.

The four Markdown findings are ordinary formatting whitespace. Removing them changes only source-line presentation; it does not change the report's scientific meaning.

## Likely causes

1. The WP13 report metadata copied the Markdown hard-break convention even though the project requires a clean `git diff --check` result.
2. The one-shot validation writer emitted standards-compliant CRLF CSV records, but the WP13 output path was not added to the existing generated-artifact line-ending policy.

## Recovery options

1. Remove the four Markdown hard-break spaces and add the narrowly scoped rule `reports/attribution/*.csv whitespace=cr-at-eol`. This preserves the frozen scientific artifact byte-for-byte while still allowing Git to detect other whitespace errors.
2. Normalize the WP13 CSV to LF and update every recorded artifact checksum and evidence reference. This is technically valid but needlessly changes a frozen one-shot output after validation.
3. Commit despite the whitespace audit failure. This weakens the repository quality gate and is not recommended.

## Recommended option

Option 1. It follows the repository's existing WP12 precedent, preserves the validated CSV checksum, and removes the genuine Markdown whitespace findings.

## User decision required

Authorize Option 1, or select another recovery option. No further Phase 3 work will proceed until this post-failure decision is recorded.
